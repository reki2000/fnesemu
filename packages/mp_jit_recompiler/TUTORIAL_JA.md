# JIT recompiler を実装から学ぶ

この教材は `mp_jit_recompiler` の**実装済み機能**を、小さなプログラムと既存コードをたどりながら理解するためのものです。CPUエミュレータの実装経験を前提にしますが、コンパイラ理論の知識は不要です。推奨順序は「まず動かす → IRを書く → 実行の境界を理解する → 正しさと最適化を考える」です。

- **実習コード**: [tool/jit_learning_lab.dart](tool/jit_learning_lab.dart)
- **実行**: `cd packages/mp_jit_recompiler && dart run tool/jit_learning_lab.dart`
- **ネイティブ版との比較**: `dart run tool/jit_learning_lab.dart --native`（利用不能な環境では参照IRインタプリタに切り替わります）
- **確認**: `dart test`
- **関連仕様**: [README](README.md) / [Frontend契約](FRONTENDS.md) / [最適化の測り方](OPTIMIZATION.md) / [未実装候補](ROADMAP.md)

ここに示す数値と結果は学習用の入力に対する期待値です。性能の数値を示すものではありません。実行環境によってネイティブコード生成の可否は異なります。

## 1. 最初に全体像をつかむ

```text
ゲストCPUの命令列
       │ デコード（CPUごとのFrontend）
       ▼
   IrBuilder → IrBlock（型付きSSA命令 + ガード + 出口 + クロック）
       │
       ▼
  JitRuntime.install
       ├─ IR検証
       ├─ 安全なIR最適化
       └─ x86-64 / ARM64 / Wasm のコード生成・登録
           （または参照IRインタプリタへの登録）
       │
       ▼
  JitRuntime.run(pc, tag)
       ├─ ブロック同士を連結して続行
       └─ miss / invalid / budget / 明示的なexit
                        │
                        ▼
                CPUアダプタが再開
            命令解釈・デバイス同期・割り込み処理など
```

**責務の分担が重要です。** `mp_jit_recompiler` はゲストCPUの命令セットを知りません。命令解釈、例外、遅延スロット、デバイス時刻などの意味を知るのはFrontendとCPUアダプタです。共有パッケージが担当するのはIRの実行、汎用的なページマッピング、コードの保護、リンク、レジスタ割り当て、生成コードの公開などです。

### 主要な部品

| 部品 | 何を提供するか | ソース |
| --- | --- | --- |
| `IrBuilder` / `IrBlock` | 型付きSSAのブロック、演算、条件付き途中退出、終端 | [ir.dart](lib/src/ir.dart) |
| `JitRuntime` | IR実行、コンパイル、コンテキスト、メモリ、キャッシュ | [runtime.dart](lib/src/runtime.dart) |
| `JitDriver` | 閾値到達時のコンパイル、未対応命令の記憶、ディスパッチ | [driver.dart](lib/src/driver.dart) |
| `JitCodeMemory` | 翻訳済みコードがあるページの書込保護と無効化 | [code_memory.dart](lib/src/code_memory.dart) |
| `JitEntryProfiles` | 初回実行時の値の観測と寿命管理 | [entry_profiles.dart](lib/src/entry_profiles.dart) |
| `JitDiagnostics` | 実行／コンパイル／終了理由の診断 | [diagnostics.dart](lib/src/diagnostics.dart) |

## 2. 実習A：IRを1ブロック実行する

`tool/jit_learning_lab.dart` の `arithmeticLab` を読んでください。ゲストレジスタに相当するコンテキストの1ワードを読み、5を加算して書き戻すブロックです。

```dart
final b = IrBuilder(0x100);
final x = b.ctxLoad(JitCtx.user);
b.ctxStore(JitCtx.user, b.add(x, b.c32(5)));
rt.install(b.finish(
  const IrExitTerm(IrExit(JitReason.user, 0x104)),
  cost: 3,
));
rt.ctx[JitCtx.user] = 7;
rt.ctx[JitCtx.budget] = 10;
rt.ctx[JitCtx.stop] = 0;
final reason = rt.run(0x100, 0);
```

**予想する結果**: レジスタは `12`、終了理由は `JitReason.user`、残り予算は `7`、終了PCは `0x104` です。

ここで区別するものは次の4つです。

- **PC** `0x100`: 実行を開始するゲスト命令アドレス。ホストの機械語アドレスではありません。
- **tag** `0`: PCだけでは区別できない翻訳条件（例: 遅延スロットや実行モード）を表すキー。
- **`JitCtx.user`**: ゲスト状態を入れる領域の先頭（現在はワード番号8）。0–7は予約領域です。
- **`cost`** `3`: ブロック全体で消費する**ゲストクロック**。ホスト側の実行時間ではありません。

`JitRuntime.interpreter` はIRの意味を実行する参照実装であり、実機CPUの既存インタプリタとは別物です。`JitRuntime.native` は対応環境で同じIRから機械語を作ります。

**確認問題**: 初期レジスタを `0xffffffff` にして5を加えると何になるでしょうか。また、予算を1にすると命令は実行されるでしょうか。

## 3. SSAを理解する

SSAは「計算結果には新しい名前を付ける」という表現です。`IrValue` は値そのものではなく、ブロック中でその値を定義した命令の位置を指します。

```text
v0 = ctxLoad(8)       // 値7を読み出す
v1 = c32(5)           // 定数5
v2 = add(v0, v1)      // 値12
     ctxStore(8, v2)  // ゲスト状態へ書き戻す
```

`v0` は変更されません。次の計算には別の `v3` を作ります。ゲストレジスタを「何度も書き換える」機械と、結果を「一度だけ定義する」IRを切り分けるのが狙いです。コンパイル時には依存関係が明確になり、定数畳み込み、不要値除去、ホストレジスタ割り当てがしやすくなります。

IRの整数値には `i32` と `i64` があり、演算は指定幅で巡回します。比較の結果、分岐条件、アドレス、PC、tag、シフト量は32ビットです。ブロックの終端は1つだけで、`IrJump`、`IrBranch`、`IrJumpDyn`、`IrExitTerm` のいずれかです。途中の `exitIf` は終端とは別の**サイドイグジット**です。

**実習**: `arithmeticLab` の `add` を `xor` に変え、`12` ではなく `7 ^ 5 = 2` が書かれることを確認してください。

## 4. ブロックを連結し、クロックを管理する

実習Bの `chainingLab` は `0x300` で1を加算し、`IrJump(0x304)` で次のブロックに移り、もう1度加算して終了します。2ブロックともインストール済みなので、途中で必ずDartに戻る必要はありません。

```text
run(0x300, tag=0), budget=10
  ├─ [0x300] r0 += 1    cost=2
  ├─ [0x304] r0 += 1    cost=4
  └─ host exit         r0=2, budget=4
```

ネイティブ側は静的リンクと動的ジャンプ表を使って実行を継続します。条件付き `IrExit(link: true)` でも、指定出口のレジスタ書戻しと未使用クロック返金の後にターゲットブロックへ連結できます。リンク先の未登録時は `JitReason.miss` が返ります。

**予算は命令ごとに割り込ませません。** ブロック入口で正の予算があれば、そのブロックが終わる（またはサイドイグジットに達する）まで実行します。したがって、最後の1ブロックの `cost` 分だけ予算が負になる場合があります。アダプタはこのオーバーシュートを考慮してデバイスや割り込みの時刻を管理します。

`IrExit.spent` は途中で出るまでに消費したクロックを示します。たとえば `cost: 6` のブロックが `spent: 2` で退出すれば4クロックを返金し、実消費は2です。`IrExit.stores` は、その退出経路でのみゲスト状態に戻すSSA値です。

**確認問題**: 予算が3、最初のブロックのcostが4、次ブロックのcostが2なら、最初のブロック後の残予算と最終終了理由は何でしょうか。

## 5. 実習C：メモリを読み書きする

`memoryLab` ではゲストアドレス `0x1000` を `rt.alloc` で確保したバッファにマッピングします。バッファの先頭4バイトが `12 34 56 78` のとき、

```dart
final x = b.load(4, b.c32(0x1000), endian: IrEndian.big);
b.ctxStore(JitCtx.user, x);
```

は `0x12345678` を得ます。メモリのエンディアンはアクセスごとに指定できます。値の保持幅と独立しており、i64値も同じ仕組みを使用します。ページサイズの初期値は4KiBで、読み込みと書き込みのマッピングは独立しています。

**未マップのアクセスには2種類あります。**

1. `unmapped:` を渡さない `load/store` はホストの `read/write` コールバックを呼びます（デバイスアクセスなどを表せます）。
2. `unmapped: IrExit(...)` を渡した `load/store` は、アクセス**前**にブロックを抜け、アドレスを `JitCtx.faultAddr` に記録します。アダプタがクロックとCPU状態を同期し、既存のCPUインタプリタで当該命令を実行できます。

`guardMapped(address, exit, write: true)` は実際にアクセスすることなく、書込可能ページの有無を検査します。読み書き両方を要する操作、ページ跨ぎ、アラインメント例外、MMIOの副作用は、CPU側が別途意味を決めます。単にメモリがマップ済みだから安全、ではありません。

## 6. コードが書き換わったらどうなるか

翻訳済みコードとゲストメモリが矛盾することを防ぐ機構は2層です。

- **命令ガード**: `b.guard(addr, expectedWord, endian: ...)` が、ブロック入口で元の命令ワードとの一致を調べます。不一致なら `JitReason.invalid` を返します。
- **コードページ保護**: `JitCodeMemory` は翻訳済み命令を含むホストページとその書込可能な別名マッピングを追跡し、ネイティブからの書込みを退出させます。`release` は翻訳を無効化して保護を解除でき、`reset` は保護状態を初期化します。

ただし、CPUインタプリタ、DMA、別CPU、ホストからの書込み経路まで**自動で全部捕捉するわけではありません**。その場合にも命令ガードが必要です。保護を解除してよい条件やページの共有は、CPUアダプタの責務です。

**考える問題**: コードとデータが同じページにあり、翻訳済みコードがそのデータへ頻繁に書き込む場合、常に書込保護する設計では何が起きるでしょうか。答えは `JitCodeMemory.noteStoreExit` を読んで考えてください。

## 7. 32/64ビット演算と浮動小数点

| 分類 | 現在の提供機能 | 注意 |
| --- | --- | --- |
| 整数 | 加減乗、積の上位半分（符号あり/なし）、AND/OR/XOR、シフト、比較、select | 指定幅で巡回、シフト量をマスク |
| 拡張 | `sext8/16/32`, `zext8/16/32`, `trunc32` | 32ビット演算結果の符号拡張をFrontendが明示 |
| メモリ | 1/2/4/8バイト、符号拡張、リトル/ビッグエンディアン | 64ビットのゲスト値は`i64`で保持 |
| 浮動小数点 | IEEEビット列の加減乗、f32⇔f64変換、整数化（最近接偶数/ゼロ方向） | 特殊値・丸め状態・例外の全仕様を再現するわけではない |
| ホスト呼出し | 3個のi32引数、i32戻り値の `call(helperId, ...)` | i64引数のhelper ABIは未実装 |

64ビット定数は `b.c64(BigInt.parse('18446744073709551615'))` または `c64Parts(low, high)` で**正確に**構築します。コンテキストに格納するときは連続2ワード（下位32ビット→上位32ビット）を占めます。これはゲストメモリのエンディアンとは独立です。

たとえば64ビットの `0xffffffffffffffff + 2` は、巡回して `1` になります。32ビットの符号つき値を64ビットのゲストレジスタへ書き戻すには、`b.sext32(b.add(b.trunc32(x64), b.c32(1)))` のように幅を明示します。

浮動小数点演算はビット列を浮動小数点として解釈します。NaNペイロードは保証されず、非有限値や範囲外の `floatToInt` は未規定です。CPU固有のFPUフラグや例外が必要なときは、Frontend側でガードしてCPUへ戻します。

## 8. ヘルパー呼び出しとレジスタ割り当て

`rt.addHelper((a, b, c) => a + b + c)` はホスト関数を登録してIDを返します。IRの `b.call(id, a, b, c)` はその関数を呼びます。**ヘルパーは任意のデバイス同期を自動的に正しくする仕組みではありません。** コールバック前後の値の保護やABIはバックエンド、どの呼び出しが安全かはアダプタが担当します。

x86-64バックエンドはブロック局所の線形走査型レジスタ割り当てを使用し、7個の汎用レジスタと8バイトのスピルスロットを扱います。コールバックを跨いで生存する値を退避し、サイドイグジット時点の値を保ちます。ARM64は現在SSA値をスタックスロットに置き、汎用レジスタへのSSA割り当ては未実装です。両者の性能特性が同じとは限りません。

## 9. 最適化は何をするか

共有のIR最適化には**i32定数畳み込み、恒等式の簡約、使用されない純粋な値の削除**などが含まれます。たとえば

```text
v1 = add(v0, 0)       → v0
v2 = mul(v1, 1)       → v0
v3 = xor(v0, 42)      → 未使用なら削除
```

一方、`load`、`call`、`guard`、サイドイグジットの状態、クロックなど**副作用や実行意味に関係する情報**は消してはいけません。生成の前にIRを検証し、異なるバックエンドでも同じ実行結果を保つことを重視しています。参照IRとネイティブ実行の差分テストが重要なのはこのためです。

x86-64では即値命令や定数の再生成なども使用します。ただし最適化のコストはゼロではありません。[PERFORMANCE.md](PERFORMANCE.md) は過去の特定条件の合成ベンチマークであり、ゲーム全体の高速化率ではありません。

## 10. JitDriver：いつコンパイルするか

`JitRuntime.install` は渡されたIRをただちにインストールします。「何回実行されたら翻訳するか」は共有ランタイムが勝手に決めません。CPUアダプタから `JitDriver` を使うと、次をまとめて扱えます。

- 同じ `(pc, tag)` への到達回数を数え、`threshold` 到達時に `translate(pc, tag)` でIRを作る
- まだ冷たいコードや翻訳できないコードをCPUインタプリタへ戻す
- 翻訳できなかった命令ワードを記憶し、変更されるまで無駄な再翻訳を避ける
- コードガード失敗時の無効化、観測情報のクリア、予算付き実行 `runBudgeted` を扱う

一方、Frontendが選ぶ命令、未対応命令の実行、レジスタ同期、遅延スロット、例外、デバイスの期限は引き続きアダプタの責務です。ホット判定は性能上の目安であって、コンパイルすれば必ず速くなるという証明ではありません。

SH-2の現行Frontendには、コールド実行でレジスタ値を観測し、安定したメモリ基底値を**ガード付きで**置き換える限定的な値特殊化があります。これは汎用のトレーシングJITが実装済みという意味ではありません。安定して見えた値でも使う前のガードが必要で、失敗した場合は正確なCPU状態に戻して汎用コードへ切り替えます。

## 11. 実行環境と共有機能

| 実行方式 | 対象 | 性質 |
| --- | --- | --- |
| x86-64ネイティブ | Linux / Windows / Android x64 | コンパイル済み機械語、SSAレジスタ割り当て |
| ARM64ネイティブ | macOS / Linux / Windows / Android ARM64 | コンパイル済み機械語、SSA値は現在スタック主体 |
| Wasm | Web（dart2js / dart2wasm） | ブロックごとのWasmモジュール、共通の関数表とディスパッチ |
| 参照IRインタプリタ | 全プラットフォーム | 実装の正しさを照合する基準 |

同じIR機能を全方式が提供します。Wasmは固定64MiBの線形メモリを使い、インストール済みブロックが4096件でコードキャッシュをクリアします。ネイティブ実行にはビルド時のCヘルパーとOSごとの実行ページ公開が必要です。ホストが未対応、またはWebのポリシーでWasmコンパイルが禁止されていると、`JitRuntime.native` は `null` を返します。共有ゲストバッファは逐次実行を想定し、並列CPU実行の同期機構ではありません。

## 12. 「速くなった」をどう判定するか

**native coverage（JITのゲストクロック比率）≠ ホストCPU使用率 ≠ FPS改善率** です。ネイティブ内で短時間しか実行せず頻繁にDartへ戻ると、ネイティブ命令自体が速くても全体は遅くなり得ます。

分析は次の順序が有効です。

1. 同じ入力、同じ場面、同じウォームアップで、AOT版のフレーム時間を測る。
2. `core_headless bench --profile-exits` で終了理由・退出PC・ゼロ仕事の呼出し・消費クロックを別測定する。
3. ヒットする未対応命令、MMIO、リンクミス、コードガード、同期・期限のうち、頻繁な境界を1つ選ぶ。
4. 最小の変更を加え、統計収集を外して同一条件で比較する。
5. 実際の入力応答、描画、音、割り込み・複数CPU同期に破綻がないか確認する。

必要に応じて `JitDiagnostics.enableExecutionStats()`、`enableCompilationStats()` を使い、測定時のオーバーヘッドも分けてください。`nativeEntries` はFFI等からネイティブへ入った回数で、連結した**個々のブロック数ではありません**。`jitClocks` は処理したゲストクロックで、ホスト時間ではありません。詳細は [OPTIMIZATION.md](OPTIMIZATION.md) を参照してください。

## 13. 演習課題（答えを見ずに考える）

1. `IrBuilder(0x100, tag: 1)` と `IrBuilder(0x100, tag: 2)` は同じブロックとして扱われるか。なぜtagが必要か。
2. `IrExit(spent: 2)` で `cost: 6` のブロックから出た場合、初期予算100は何になるか。
3. `i32: 0xffffffff + 5` の結果はいくつか。`i64: 0xffffffffffffffff + 2` はどうか。
4. `load` で未マップ領域に触れた場合、ホストreadを呼ぶ場合とCPUへ戻る場合はどう使い分けるか。
5. ゲストRAMのコードページを別のアドレスにもマップしている場合、片方だけ書込保護してよいか。
6. `jitClocks/cpuClocks` が90%になったら、ホスト時間も90%をJITが占めていると言えるか。
7. 新しいi64命令をIRに加えるとき、参照実行器だけを変更して完了と言えるか。
8. 命令ワードが変わった直後に、古い生成コードをそのまま実行してよいか。
9. `JitRuntime.install` だけを使うプログラムで、ホット判定は誰が担当するか。
10. 短いブロックをただ長くすれば、MMIOによる途中退出は必ず減るか。

<details>
<summary>解答と理由</summary>

1. 別ブロック。`(pc, tag)` がキーで、実行モードや遅延スロットの状態を区別できる。
2. `98`。未実行分4クロックを返金するため、実消費は2。
3. `4` と `1`。値幅ごとに巡回する。
4. `unmapped:` 未指定ならコールバック、指定ならアクセス前に退出してCPUが扱う。副作用や同期の必要性で選ぶ。
5. 不可。書込みを許した別名から翻訳済み命令を変えられる。
6. 言えない。比率の分母はゲストクロックであり、ホストCPU時間ではない。
7. 言えない。参照実行器、x86-64、ARM64、Wasmのすべてが同じ契約を満たす必要がある。
8. 不可。命令ガード失敗として無効化し、再翻訳やCPUフォールバックを行う。
9. 呼び出し側。共有の閾値・キャッシュ・フォールバック処理を使いたければ `JitDriver` を利用する。
10. 必ずとは言えない。退出理由がメモリやデバイス境界なら、ブロック長だけ変えても避けられない。

</details>

### この教材で扱っていないこと

実機CPU命令の網羅性、CPUごとの例外再現、MMIOの安全性、割り込みと他CPUの同期はFrontend／アダプタに依存します。また、本教材の実習プログラムは汎用ランタイムAPIのデモであり、既存コアのベンチマークや互換性テストを代替しません。
