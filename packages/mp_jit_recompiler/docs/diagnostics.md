# Diagnostics

All diagnostics are optional and perturb execution. Collect each of them in a run separate from the throughput comparison. The workflow that uses them is in the [performance guide](performance.md).

## Interface

Each frontend supplies a `JitDiagnostics` descriptor, and cores enumerate them in CPU order through `CoreDebug.jitDiagnostics`. Tools therefore use one interface for every core. Instruction inspection reads only existing mappings, respects buffer offsets and alignment, and never invokes bus callbacks.

JIT usage shown in the app is the fraction of guest CPU clocks executed by a compiled backend, sampled over the same 500ms windows as FPS. It is not a host CPU-time or speedup measurement.

## Execution statistics

`JitDiagnostics.enableExecutionStats()` installs a recorder on the bound CPU adapter, and `disableExecutionStats()` removes it. The shared collector keeps bounded dispatch sites and memory groups, reports overflow while preserving totals, and supports interval resets with `clear()`.

- CPU dispatch clocks and idle clocks are separate. Selected opcodes can be unavailable or superseded by interrupt service.
- Memory reports count CPU-side fetch, read and write bus requests, including synchronous nested requests, rather than direct mapped native accesses.
- Frontends supply region labels. Labels confer no memory permissions.

`core_headless bench --profile-cpu` reports these statistics. A compiled backend must be available even with `--jit off`; that mode suspends compilation and uses the interpreter on the shared buffers.

## Compilation statistics

`JitDiagnostics.enableCompilationStats()` enables, on its runtime, the collection of translation and publication timing, generated payload bytes, driver entry-cache lookups, fallback-cache hits, guard failures and cache lifecycle events. `disableCompilationStats()` removes the recorder, and `clear()` resets observations without clearing compiled code.

- Translation timing covers the frontend callback. Publication timing covers IR verification, optimization, backend emission and publication, including any cache-capacity retry.
- Native payload sizes exclude padding and shared stubs. Wasm sizes include each emitted block module. Reference IR installations report zero generated bytes. Bytes accumulate across installations and do not represent resident memory.
- Driver lookups exclude native block links. Actual invalidations and bulk clears are distinct from driver observation-cache clears.
- Per-site storage is bounded. Totals survive overflow, and `repeatInstallsAtRetainedSites` counts repeated successful installations only at retained `(pc, tag)` sites in the current interval. These sites do not identify distinct code versions.

`core_headless bench --profile-compile --jit on` reports these statistics as `compilationProfiles`.

## Native-return profile

An invocation starts at an actual Dart-to-native FFI entry and ends when native execution returns to Dart. It may execute several linked blocks or no guest instructions. The tools also call this unit a native entry, return or exit. A compiled block, a native invocation and an interpreted instruction are different units.

`core_headless bench --profile-exits` attaches after warmup without clearing compiled blocks. `nativeExits` reports each runtime in CPU order, including master and slave for SH-2. It groups count, cycles, zero-work returns and mean entry budget by cause and by entry PC, exit PC, mapped exit opcode and fault page. At most 4,096 sites are retained per runtime and the top 40 are printed. Totals include overflow and must equal the interval native-entry and JIT-clock deltas.

`unmappedOrDevice` and `protectedOrReadOnly` describe current mappings rather than hardware proofs. `stopYield`, `codeGuard`, `linkMiss`, SH-2 `profileGuard` and `unsupportedInstructionOrSlot` identify other boundaries. Opcode bytes are read only from existing mappings, and sites with different exit instructions are separate code versions. Sites include the first exact fault address and the varying address bits where available. A `0xffffffff` fault sentinel means the exact fault address is unknown. The profile aggregates synchronously at native return and does not observe individual linked blocks.

How to read each cause:

| Observation | Investigation |
| --- | --- |
| Zero-work budget returns | Check why the host enters with a zero or negative budget; blocks entered with a positive budget always run |
| Short positive spans despite ample budget | Inspect the exact exit instruction, branch slot, fault address and mapping |
| Device or unmapped returns | Determine the hardware semantics in the adapter; distinguish ordinary unmapped memory from real MMIO before adding a mapping or helper |
| Protected or read-only returns | Distinguish ROM, active code and ordinary data sharing a protected page; audit aliases and writes |
| Stop or idle returns | Keep the existing multi-block idle recognition and wake paths |
| Unsupported instructions | Implement measured hot operations or batch fallback safely; static opcode coverage alone does not establish benefit |
| Missing links | Inspect hotness, invalidation and successor compilation; avoid repeatedly probing known unsupported PCs |
| Frequent scheduler entries | Count useful wakeups and next-device deadlines before optimizing device methods; keep IRQ, communication and timer ordering |

Read helpers must preserve live values and the host ABI. Only the adapter can establish that a register read is safe without synchronization. A guarded pointer literal can be constant while the value read through that pointer stays live. Helpers can extend native coverage yet lose throughput through callback costs.

## Block profile

`--profile-blocks` clears installed blocks after warmup to add entry callbacks. Remaining-budget differences and refunds determine the positive consumed spans. The histogram cycle sum must equal the compiled-clock delta, and its mean and p90 are weighted by execution count, not by cycles. Clearing code can change early fallback and coverage relative to a warm-cache run. An installation histogram describes compiled code, not dynamic execution.

## Interval metrics

Exclude warmup from every delta and state the unit and denominator explicitly.

| JSON field or statistic | Definition |
| --- | --- |
| `msPerFrame` | Elapsed core execution and `imageBuffer()` time divided by measured frames; document any audio callback work included |
| `cpuMsPerFrame` | Process CPU time per frame when supported; distinguishes execution work from descheduling |
| `cpuClocks` | Total guest CPU clocks, including idle and sleep; sum both CPUs for SS and 32X |
| `jitClocks` | Guest clocks actually consumed by the compiled backend |
| `jitCyclePercent` | `100 * jitClocks / cpuClocks`; null when no CPU clocks elapsed |
| `nativeEntries` | Actual FFI entries, including zero-work returns; excludes missing-block lookups before entry |
| `meanNativeExitCycles` | `jitClocks / nativeEntries`; null when there were no entries; includes zero-work returns |
| Executed block mean and p90 | Execution-weighted consumed cycles of individual positive block spans, including partial side exits; excludes fully refunded entries |

The native-entry counter is one integer increment per compiled-code invocation (an FFI call on native hosts, a dispatcher call on Wasm) and needs no per-block callback. Reference IR execution does not count entries. The tools report cycles per invocation and per block, not guest instruction counts or blocks per invocation. Collect those separately if needed; do not relabel cycles as instructions.

Guest-clock coverage is neither a host CPU-time share nor a speedup estimate. If idle dominates, additionally report idle, native and interpreted clocks and an explicitly named idle-excluded native ratio, and keep the original denominator for comparisons. Mean cycles can rise solely because zero-work calls disappear, so also report the zero-work rate and the positive-span distributions. Entry counts per second, entry-budget distributions, compile time, generated bytes, profile memory and GC are useful follow-up metrics when the hypothesis requires them.

N64 has `--jit-stats` (`n64Stats`): skipped idle clocks, CPU fallback selections by raw opcode, and runtime exits by reason and raw opcode. A selection at the current PC can service an interrupt before that opcode executes, so these counts are not an instruction trace.
